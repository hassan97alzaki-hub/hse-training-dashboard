# خطة إصلاح تعديل السجلات المستوردة وقياس «رفعوا بيانات»

**الحالة:** مقترح للمرجع. لم يُنفَّذ أي كود.
**التاريخ:** 2026-10-25. **الأساس:** `main` على `08ad3b9`. **العيوب:** BL-004 إلى BL-008 في `docs/BACKLOG.md`.

## 1. الخلاصة

1. PR #14 (`fix/import-record-id`) مدموج منذ 2026-10-24، لكن فحص المتصفح بعد الدمج أظهر أن تعديل السجل المستورد ما زال معطوباً: التعديل لا يظهر (BL-004)، وإعادة الاستيراد تنتج نسخة مكررة (BL-005)، وخانة الكورس فارغة (BL-006).
2. معرّف السجل المستورد `imp_row_<رقم الصف>` قد يتصادم بين مساحات العمل في السحابة، لأن `training_records.id` مفتاح أساسي على مستوى الجدول كله (BL-007). هذا من قراءة الكود، ولم يُختبر على الإنتاج.
3. **الأهم للقرار:** الاستيراد لا يحفظ أي صف في قاعدة البيانات أصلاً (BL-008). لذلك بند البوابة «رفعوا بيانات تدريب فعلية» لا يعدّ من رفع ملفاً، بل من سجّل أو عدّل سجلاً يدوياً فقط. والرقم الحالي أقل من الواقع.

## 3. فحص الإنتاج المقترح قبل أي قرار (المالك، قراءة فقط)

في SQL Editor بصلاحية المالك. لا يحتاج حسابات اختبار:

```sql
-- هل كتب أي مستخدم تعديلاً على صف مستورد؟ (أثر PR #14)
SELECT workspace_id, count(*) AS imp_rows
FROM public.training_records
WHERE id LIKE 'imp_row_%'
GROUP BY workspace_id;

-- كم مساحة تجربة فيها أي صف تدريب، مقارنةً بعدد المساحات
SELECT
  (SELECT count(*) FROM public.workspaces WHERE trial_ends_at IS NOT NULL) AS trial_workspaces,
  (SELECT count(DISTINCT workspace_id) FROM public.training_records) AS workspaces_with_rows;
```

وفي سجلات Supabase (Postgres logs): البحث عن `duplicate key value violates unique constraint "training_records_pkey"`. وجوده يؤكد BL-007 على الإنتاج.

### 3.1 نتيجة الفحص (المالك، 2026-10-25)

| الرقم | القيمة |
|---|---|
| `trial_workspaces` | 0 |
| `workspaces_with_rows` | 1 (غالباً مساحة المالك) |
| عدد صفوف `imp_row_%` لكل مساحة | **0 صفوف** (المالك، 2026-10-25، الاستعلام الأول وحده: «Success. No rows returned») |

الخلاصة: لم يتأثر أي مستخدم تجربة حتى الآن، **ولا يوجد أي صف `imp_row_*` في الإنتاج**، فلا صفوف قائمة يمسها التصادم ولا حاجة لأي جراحة SQL. شرط R-2 مستوفى.

### 3.2 حالة القرارات (SPECS v1.4، 2026-10-25)

| القرار | الحالة |

## 5. خطة الإصلاح

### المسار 1 — عاجل وصغير (لا migration، لا تغيير في المحرك)

| Commit | المحتوى | يعالج | اختبارات |
|---|---|---|---|
| F1 | معرّف فريد لكل صف مستورد: `imp_<UUID>` بدل `imp_row_<n>` | BL-007 | المعرّفات فريدة بين ملفين ومساحتين؛ لا يتكرر المعرّف عند إعادة الاستيراد |
| F2 | بعد حفظ تعديل سجل مستورد: يُستبدل في `importedRecords` أيضاً، لا في `manualRecords` فقط | BL-004 | الجدول يعرض القيمة الجديدة فوراً؛ لا تتغير أعداد السجلات |
| F3 | قائمة الكورس في نموذج التعديل تتضمن كورس السجل المستورد حتى لو لم يكن مسجلاً | BL-006 | الخانة تعرض الكورس الصحيح |

| F5 | (إذا اعتُمد R-1-ب) حدث «استيراد ناجح» لكل مساحة: التاريخ وعدد الصفوف فقط، بلا محتوى، مع استعلام قياس | BL-008 (البند 3) | يحتاج migration صغيرة لجدول أحداث؛ تُعرض للمرجع قبل التنفيذ حسب قاعدة 2026-10-20 |

**ملاحظات:**
- صفوف `imp_row_*` الموجودة في الإنتاج تبقى كما هي، ولا تُعدّل بلا موافقة (قاعدة «أي جراحة SQL تُرفع للمرجع»).
- المسار 1 لا يحل BL-005 بالكامل: سيبقى التعديل المحفوظ والصف المستورد سجلين عند إعادة الاستيراد بعد إعادة التحميل. الحل الكامل في المسار 2.

### المسار 2 — بعد البوابة

حفظ دفعات الاستيراد في السحابة لكل مساحة، بحيث يعدّل التعديلُ الصفَّ المحفوظ نفسه، ويكون للسجل معرّف ثابت. يتوافق مع مواصفة `HSE-DC-1.0` (staging ومعاينة واعتماد، ومفتاح `(source_system, source_record_id)`). يعالج BL-005 والبند 1 من BL-008. يحتاج وثيقة مرحلة معتمدة وmigrations.

## 6. معايير القبول للمسار 1

1. تعديل سجل مستورد يظهر في الجدول فوراً، دون تكرار، في Local Mode والسحابة.
2. مساحتا عمل تعدّلان الصف رقم 2 من ملفيهما دون أي خطأ، ولا ترى إحداهما صف الأخرى.
3. تعديل صف من ملف ثانٍ لا يغيّر سجلاً محفوظاً من ملف سابق.
4. خانة الكورس تعرض كورس السجل.
5. كل الاختبارات الحالية تنجح (1267 حالياً)، مع اختبارات جديدة لكل commit.
6. فحص متصفح موثق قبل الدمج، وفحص على الإنتاج بحسابي تجربة يجريه المالك بعد النشر.

## 7. الرجوع

كل commit مستقل ويُرجع بـ `git revert`. المسار 1 لا يغيّر قاعدة البيانات (عدا F5 إن اعتُمد، وله migration عكسية تُعرض مع الطلب).
